## 1. 引言

给定一张图像,作业要求把它转换成一个由三角砖构成的镶嵌图,
在不超过 10,000 个独立直角等腰三角形的硬预算下,视觉上逼近原图,
无间隙且无重叠,每块砖带一个由其覆盖区域决定的均匀面色。
允许多种砖的尺寸和多种颜色。

"无间隙/无重叠" 是一条硬约束,所以我不想把它单独靠在构造论证上。
`code/verify_coverage.py` 对三个交付的铺覆直接检查这一条:单元格子是
互不相同的、网格对齐的,每个单元的两块三角形满足精确的面积恒等式
`area(a) + area(b) == s²` (对顶点用鞋带公式),光栅化三角形后在交付的
裁剪区域内留下 **0 个未覆盖像素**。这一测试是基于几何而非基于光栅化的
"重数"计数,因为 `cv2.fillPoly` 会在每条内部对角线上画出一像素的边带——
这是一个光栅化约定而非面积重叠,我在 §4.3 中单独量化了它。三个结果
都通过。

由于预算固定,真正的工作是决定细节应该放在哪里。更多的三角形能捕获更多
的边缘和纹理,但也让每块砖的颜色估计更不稳定(很小的三角形只平均很少的像素,
传感器噪声就会看起来像细节),而且这些都不能解决把每个区域映射到固定调色板
项所带来的颜色误差。我把这三件事分开看,让每个 task 在当时去攻最该攻的那一块。

我把系统分成四个阶段搭出来,每一阶段都会冒出一个塑造下一阶段的问题。
Task 2 把铺覆固定成等大砖块加三种颜色;测量它的输出可以看到均匀网格
没有对齐图像内容,这成为了 Task 3 的动机。Task 3 让几何和调色板都变成
自适应的,这才真正回答了上面那个预算分配问题。Task 4 把同一套管线
跑进实时相机循环里,这时离线设置所掩盖的速度和稳定性问题就成了
主要的工程工作。

**测试图像。** 本报告的测试照片是 `code/pics/sky.jpg` (1706x1279),
一张运河一侧的城市场景——砖墙、树木、远处的建筑——用 Task 1 所用的相机
拍摄。它的主导信号是亮度变化而不是色相变化,这对颜色量化实验 (§4 和 §5)
有可测量的影响。

**预算语义。** 上限是 10,000 个 *三角形*("砖");四叉树的叶子单元产出
2 个三角形,所以一个 4,995 个单元的分区把预算用到 9,990 个三角形。
所有 Task 3 运行用 9,988-9,990 个三角形,即预算的 99.88-99.90%。

**指标评估区域。** §3-4 中的所有 PSNR/SSIM/ΔE/Edge/EPI 数值都在画上
1-px 边框的渲染画布上算。边框是 `#3C3C3C`,在所选的 Task 3 渲染上覆盖
11.6% 的像素,所以它是每次运行都共享的一个恒定混杂因素;它的影响在
§5.6 中被量化。9 个质量指标分别是 PSNR、SSIM、MS-SSIM、ΔE2000、
Edge F1/Precision/Recall、EPI 和量化误差,预算利用率单独作为一条约束
来跟踪。附录 A 给出每个指标精确定义和方向,因为其中几个是有意彼此冲突的。

## 4. Task 2 — 等大三角形,3 色

### 4.1 设计与测试

铺覆是一个均匀的 SxS 网格,被棋盘格对角线切开。网格步长是满足
`2·M·N <= 10000` (M=ceil(H/S), N=ceil(W/S)) 的最小 S。
三种颜色的对比是在完全相同的几何和均值上,比较三种量化方法。
主要的是 Multi-Otsu:对 BT.601 亮度直方图做穷尽的双阈值搜索,
每类用其成员的 BGR 均值上色。作为基线,我也跑了在 BGR 上的
K-Means K=3 (K-Means++ 初始化),以及在亮度直方图的 33%/67% 处
的固定百分位切分,最后一个是有意做成的不管场景统计的朴素基线。

*怎么测的。* 三种共用同一几何 (59x78, S=22, 9,204 个三角形,`sky.jpg`),
所以只有量化器不同;每个方法都跑完整的 10 项指标套件。输出:
`code/pics/task2/out_task2_compare.png` (原图 + 3 个渲染),
`out_task2_residual.png` (逐像素 ΔE2000 热力图),
`out_task2_metrics_chart.png`。

### 4.2 结果

**表 2. Task 2 结果:在相同几何 (59x78, S=22, 9,204 个三角形,sky.jpg) 上三种颜色量化器的对比。**

| 指标            | otsu   | kmeans | fixed           |
| ----------------- | ------ | ------ | --------------- |
| PSNR up (dB)      | 16.15  | 16.16  | 15.56           |
| SSIM up           | 0.332  | 0.334  | 0.286           |
| MS-SSIM up        | 0.482  | 0.481  | 0.452           |
| ΔE2000 down      | 11.41  | 11.41  | 11.92           |
| Edge F1 up        | 0.191  | 0.189  | **0.233** |
| Edge Precision up | 0.151  | 0.150  | 0.171           |
| Edge Recall up    | 0.261  | 0.255  | **0.365** |
| EPI up            | -0.028 | -0.031 | -0.012          |
| Quant Error down  | 8.47   | 8.48   | 8.98            |

这张表里三件事很突出。第一,otsu 和 kmeans 在这个场景下分不出高下:
调色板每个通道最多差 2,SSIM 只差 0.002 (0.332 对 0.334)。在 BGR 上的
K-Means 在这里塌缩到了 Multi-Otsu 直接用的那同一个一维亮度切分上,
因为这里的主导信号是亮度而不是色相;它理论上在颜色分辨率上的优势
在一张近乎灰度的图像上根本没显出来。

第二,更有意思,`fixed` 在每个边缘指标上都胜出,而在每个颜色和结构
指标上都输。它的均匀 33%/67% 阈值碰巧把更多原始边缘正好放在相邻两块
三角形之间的颜色边界上,所以那些边缘能以硬边界的方式活下来。Otsu 和
K-Means 把阈值推向感知上有意义的切分(天空对墙),反而把细的边缘给
磨平了。这里真的存在感知保真度和原始边缘保留之间的取舍,哪种方法
"更好" 取决于你说的"质量"指的是什么。

第三,三种方法的 EPI 都是负的(约 -0.03)。EPI 为负意味着输出在原图
强边缘的地方弱、在原图弱边缘的地方强:规则网格在取代它和图像内容
无关的边界。这就是均匀网格几何失配的定量签名,也是我在 Task 3 里
转向自适应铺覆的主要原因。

### 4.3 发现的问题与解决

第一次跑只产出了两个三角形,因为 `compute_grid` 把 S 从大往小扫,
返回了能塞进预算的最大 S,这对这张图来说就是 1x1 网格。代码语法上
没问题但语义上错了;循环必须把 S 从小往大长,返回留在预算内的最小 S。
我把扫描方向反过来修了(`code/brick_geom.py::compute_grid`)。

网格还留下了一条黑边。基于 floor 的网格把不够凑成完整 SxS 正方形的
尾行尾列丢掉了(`sky.jpg` 上右边 5 像素、下边 19 像素),那些像素保持
黑色,把 PSNR/SSIM 误差撑大了。我通过换成 `ceil` 网格、把图像
reflect-pad 到 `M·S x N·S`、渲染、再裁回原尺寸来修(`code/triangle_brick.py::preprocess`)。
修完之后 SSIM 从 0.3226 升到 0.3316,PSNR 从 15.76 升到 16.15 dB;
修复前的数字留在 git 的 `a5d2d76` 这个 commit 里,如果要直接的
修复前/修复后对比的话。

网格选择的那个 bug 来自一段 AI 写的草稿:模型把 `compute_grid`
的循环写成扫描方向反了,代码语法上是合法的,只有手动把逻辑逐行
过一遍——追踪这个循环对大图像到底返回什么——才看出它是错的。
我人工把它改正了。这个片段说明,AI 生成的逻辑并不保证正确,
对每一段这样的函数,都需要一步一步核对它的控制流,而不是因为它
能跑就信任它。

## 5. Task 3 — 自适应多尺寸、多颜色

### 5.1 设计与测试

我在 Task 2 上加了两块自适应。铺覆现在是 **自顶向下的 RDO 四叉树**,
从粗网格开始,在预算还够时拆最高优先级的单元(ΔMSE/6);调色板
现在是 **K-Means-Lab** 且 K>3,Median-Cut 留作基线。我把 Task 2 的
主量化器(Multi-Otsu)拿掉了,因为 Otsu 是一维亮度方法,产出不了
超过很少几个阈值类。Task 3 需要任意 K 色的调色板,所以我用一个
感知均匀的 Lab 空间上的一般聚类方法取代了它。

**区域合并(对偶算法)。** 作为自顶向下四叉树的对照,我也实现了
自底向上的区域合并(`brick_region_merge`)。它从最小允许尺寸的单元
开始,在三角形预算允许时,用 summed-area 表给每个合并候选打分,
贪心地把对齐的 2x2 等大单元块合并成一个边长翻倍的单元。合并候选
是在 `target_size` 网格上生成的,这样每个合并出来的块本身又能
组成下一层的 2x2 块。在 `sky.jpg` 上它在 9,990 个三角形、44,415 次
合并处终止,最终尺寸分布只到 {16,32} (它把所有细单元都合并掉了),
这就是 §5.2 里它和四叉树对比时所依赖的那个性质。

我设计了一个 15 次运行的实验网格,每次只改一个变量、其余全部固定,
这样任何指标差异都可以归因于这一个变量。每一组实验回答一个具体的
设计问题:

| 组 | 改动的变量(其余全固定) | 要回答的设计问题 |
| --- | --- | --- |
| A_ksweep | K ∈ {4, 8, 16} | 更大的调色板能改善颜色误差吗?代价是结构吗? |
| B_sweep | S_min ∈ {2, 4, 8}(..32) | 从允许集合里去掉最小单元有影响吗? |
| B2_smax | S_max ∈ {32, 64, 128} | 从更粗的起始网格开始(给深拆分留更多预算)会改变结果吗? |
| C_algorithm | 分区:quadtree vs region-merge | 哪种铺覆策略——自顶向下 RDO 还是自底向上合并——更好? |
| D_palette | 调色板:K-Means-Lab vs Median-Cut | 几何固定时,哪种调色板方法在颜色和结构上胜出? |
| E_priority | 优先级:ΔMSE vs Sobel 边缘密度 | 拆分优先级影响边缘对齐吗,还是 ΔMSE 才是对的? |

所有运行用 9,988-9,990 个三角形,即预算的 99.88-99.90%。完整表在
`code/pics/task3/summary/metrics_table.csv`。

### 5.4 S_max = 32 vs 64 —— 一个双侧的取舍

"S_max=64 胜" 的指标结论只是故事的一面。把 ΔE 按区域和单元尺寸拆开看
就看到另一面。我把下面的曲线用 **确定性 Median-Cut 调色板** (K=8) 重跑
了一次,这样把 S_max 的几何效应和 K-Means-Lab 一次跑和下一次跑的方差
隔开,所以它的数值和 §5.2 的 K-Means-Lab 行不能直接比(那里 S_max=32
给出 ΔE 9.95,S_max=64 给出 10.21)。两次扫描在 *方向* 上一致,在量级
上不同,图在 `code/pics/task3/analysis/smax_curve.png`。

**表 5. S_max 扫描(确定性 Median-Cut 调色板,K=8):感知对结构指标。**

| S_max                   | 32              | 64    | 128   | 256   |
| ----------------------- | --------------- | ----- | ----- | ----- |
| ΔE2000 (lower better)  | **10.61** | 11.77 | 11.79 | 11.79 |
| SSIM (higher better)    | 0.375           | 0.415 | 0.415 | 0.415 |
| Edge F1 (higher better) | 0.322           | 0.403 | 0.402 | 0.402 |

ΔE2000 在 S_max=32 处最好,之后恶化,然后变平。SSIM、Edge F1 和 EPI
升到 S_max=64 然后变平。并不存在唯一最好的 S_max:32 赢在大面积颜色,
64 赢在结构和边缘,而哪个是 "最优" 取决于你怎么加权这两面。为了验证
而不是断言这一点,`code/task3_shadow_crop.py` 把 **源** 图像按亮度
百分位切成两堆像素集(最暗的 40% 和其余),对两组分别算逐像素
CIEDE2000 图的均值,在两个 S_max 值上都做。在源上而不是在任一渲染上
定义这个分割,才是让两者可比的那件事。在 S_max=64 下,阴影那一堆的
平均 ΔE 从 8.37 升到 10.90,**+30%**,而亮区那堆几乎不动(12.11 到
12.35,**+2%**)——退化集中在暗区,这恰好是 ΔMSE 优先级已经没有方差
可以拆分的地方。两个数字都来自那个脚本:`crop_shadow.png` 和
`crop_sky.png`,非高亮那一组被压暗,这样每张图都只显示自己的像素。
我在本报告中选了一个折中的配置(§5.6)。

这个取舍背后的机制是 RDO 优先级是 ΔMSE,它随局部方差缩放。边缘被
拆分,平滑区域永不被拆分,所以一整片大面积最后被涂成单一颜色,其
逐像素误差小但 *累计* 感知误差大。ΔMSE 看不见大面积的均匀漂移,
但眼睛能。

在上面的两类指标上,S_max=64 赢四个客观分,而人眼和那个唯一的感知
颜色指标(ΔE2000)都更喜欢 32。唯一和人眼一致的指标,正是那种只靠
指标的总结可能会想丢掉的那一个。两个量在度量不同的事:逐像素的结构
对累计的大面积颜色漂移。两者都不是 "答案"。这就是为什么 §5.6 选
了折中配置而不是宣布单一胜者,而同一件事在 §7.1 里又作为 AI 的
报告偏差再次出现。

### 5.5 发现的问题与解决

第一个问题是 AI 引入的四叉树循环反向 bug。原始代码把 `if n_tri <= budget: return`
当 guard,循环写成 `while n_tri > budget`,这反映了一个错的心智模型:
拆分 *增加* 三角形数,所以循环必须 *当* 预算还有时 *跑*。在 `sky.jpg`
上四叉树从来不拆,只用了 9,990 中 4,320 个三角形。我把它修成
`while heap and n_tri + 6 <= budget`,然后 945 次拆分正好到达 9,990
个三角形,EPI 从负变正(-0.043 到 +0.049)。我把这件事记作 AI 引入的
bug,放在 §7。

第二个问题是区域合并的候选对齐。在每个半像素偏移上生成的合并候选
落到了 `target_size` 网格之外,无法组成下一层的 2x2 块,所以运行
卡在 8,640 次合并。我在把它们生成在 `target_size` 网格上对齐之后修了
这个,此后 region_merge 在大约 1.7 s 内、经过 44,415 次合并达到 9,990
个三角形。

0.213——但那次失败是在边缘对齐上,而不是在单元尺寸覆盖上,而单元
尺寸覆盖才是这里在比较的那个性质。四叉树保住了 {4,8,16,32} 的混合,
为 +0.32 的 ΔE 换来好得多的结构分。这个对比是可复现的:
`task3_best.py` 给 OpenCV 的 RNG 设种,并把每份配置的指标 JSON 写到

## 6. Task 4 — 真实相机场景

### 6.1 这个 task 必须解决的问题

当我在 1706x1279 的参考图像上第一次跑 Task 3 的离线管线时,分区、
均值、渲染、指标加在一起约 0.1 FPS,所以速度问题在 Task 4 开始之前
就已经摆在桌上了。Task 4 把 §5.6 的所选配置丢进一个 640x480 的
相机循环,正是这时候离线设置所掩盖的速度和稳定性问题成了我必须
解决的核心工程问题。

把同一条管线搬进实时环境,问题以两种具体的方式改变。第一,一帧
必须在下一帧到来之前完成,所以每帧的成本现在有了一道离线运行从未
面对过的硬上限。第二,输出必须在帧与帧之间保持稳定:不能只是因为
传感器噪声移动了几个灰度级,镶嵌图就每帧明显重新组织一次。这两条
约束在离线设置里都是看不见的——那里每次运行都是单张图像,既没有
截止时间,也不记得前一帧——而它们恰恰是这个 task 真正的工程内容。

我把实时处理当主线来抓,因为把管线做快本身也是弄清它真正哪里有
问题的最自然办法。先做 profile 然后只修 profile 指出来的东西,结果
证明就是撑起整 task 的方法:§6.4 里的每一处改动都源自一个测出的
瓶颈,每一个都配了对的、促成它的前后数字。交付物是 `code/camera_app.py`,
一个用 CAP_DSHOW 在 640x480 打开相机的实时循环,每帧跑完整管线,
并在一个可调整大小的窗口里把输入和渲染并排显示,带一个紧凑的 HUD
(q 退出, s 抓拍, p 暂停, r 重置)。我还做了一个 headless 的
`--no-show --input <clip>` 模式,这样这一节里的每一个数字都可以
在没有相机的情况下复现;`code/task4_verify.py` 是断言套件,
`code/task4_verify_util.py` 装助手。

成本(两次采样的中位数就是它们的均值);用 30 帧的运行,该阶段是
每帧 3-25 ms。我学到了不去从太短的运行上读各阶段百分比,因为那个
统计还来不及有意义。每张表的帧数:0.45-FPS 的基线是 8 帧运行;修正
后的调色板数字是 30 帧运行;按阶段隔离的数字是单帧重复或 12 帧配对
运行(细节在 `docs/progress/Task4.md`)。

### 6.4 满足实时约束

**Step 1: 均值颜色。** 交付的 `triangle_means_bgr` 有一个真实的缺陷,
不仅仅是速度问题:`cv2.fillPoly` 沿每个三角形的右、下边画出一像素的
边带(像素中心属于邻接单元的那些像素),所以每个 Task 2/3 砖的颜色
都被它右下邻居污染。泄漏在尺寸-1 的砖上可达 400%,在整体上约 8%
的像素。我在 `code/brick_means.py` 里加了两个新实现:

**表 10. 均值颜色实现:速度和品质(640x480, 9,990 砖)。**

| `--means`                    | FPS            | means stage       | whole frame      | ΔE2000         | PSNR               |
| ------------------------------ | -------------- | ----------------- | ---------------- | --------------- | ------------------ |
| mask (shipped)                 | 0.41           | 1716 ms           | 2260 ms          | 9.947           | 14.90 dB           |
| **fast** (exact in-cell) | **1.35** | **20.8 ms** | **532 ms** | **8.633** | **15.33 dB** |
| sample (9 interior pts)        | 1.47           | 5.2 ms            | 493 ms           | 10.244          | 14.87 dB           |

`fast` 在该阶段上快 82 倍,整体快 3.3 倍,*并且*更接近源(ΔE 9.95 -> 8.63),
因为它只平均单元内的像素。`sample` 是最快的,但在尺寸-1 砖上甚至比
那个泄漏的参考还差(在 1-4 px 三角形内部没东西可采)。这个缺陷不是
角落情况:在真实的 4,995 单元分区上,参考实现平均进 8.1% 的外来像素
(2,297,721 中的 186,021),每三角形均值与正确的单元内均值平均每个
通道差约 3.0 个灰度级(最大 46.1)。每个记下的 Task 2/3 数字都继承
了这个小的方向偏差,但因为所有运行都用了同一个泄漏参考,跨运行比较
不受影响;修正后的单元内均值就是报告里 Task 2/3 数字在没有边带时
会给出的值——一个已声明的局限。(用 `code/brick_means.py` 里的
`compare_means` 量化;完整数字在 `docs/progress/Report_prep_assets.md`
§3。)

**Step 2: 分区。** `quadtree_partition` 在每个拆分候选上重算一次 numpy
的 region mean。两个修复:把每次拆分的 4 次死的 SSE 计算去掉
(436 -> 326 ms),然后用 **summed-area 表** (O(1) 矩形 SSE) 取代
numpy region mean,批处理化让约 160,000 次小的按候选调用塌成每次
拆分一次查询。隔离:

**表 11. 分区实现:summed-area 表对 numpy 参考。**

| Implementation        | 2000 bricks | 5000 bricks | 9990 bricks      |
| --------------------- | ----------- | ----------- | ---------------- |
| ref (numpy)           | 80 ms       | 173 ms      | 326 ms           |
| sat (tables, batched) | 44 ms       | 69 ms       | **107 ms** |
| speedup               | 1.8x        | 2.5x        | **3.0x**   |

在 `mse` 优先级下分区是 **逐字节相同** 的(单元集合和尺寸分布完全一致),
所以没有任何一个 Task 3 的结论被推翻。提醒:用表实现的 `edgef1` 优先级
用全局 Sobel 图,和记下的 per-region-Sobel 运行在数值上**不相等**(在
区域边缘附近中位数约 2x 相对差);记下的 E_priority 数字被钉在
`docs/progress/Task3.md` 和 `metrics_table.csv` 上,代码在使用这一
组合时打印一条显式说明。结论(ΔMSE 胜 Sobel 优先级)在两种实现下都
成立。

**Step 3: 整管线的分析。** 把均值和分区修好之后,帧约 216 ms,剩下的
瓶颈是分区约 107 ms (约 50%, 1,565 次贪心拆分,往 300 单元起始网格
上加 4,695 个单元,成本由 numpy 调用次数主导而不是算术)、渲染约 55 ms
(约 25%, 约 20,000 次 Python 到 cv2 跨越)、调色板约 23 ms (约 10%,
每帧 K-Means)、三角形约 13 ms。我做了四处优化(除特别说明外都精确)。
优化 A 是一个按颜色分组的批渲染,把最多 K 次 `fillPoly` 调用和一条
`polylines` 合到一起,把渲染从 55 ms 降到约 8 ms 且 **0 像素不同**。
优化 B 把拆分优先级预算出来,先把约 102k 候选全部打分,让贪心循环
是纯 Python;分区从 107 ms 降到约 30 ms,叶子逐字节相同。优化 C 把
调色板刷新节奏改成每 10 帧重建一次,中间保持字节稳定,把调色板从
每帧 22.0 ms 摊到 4.9 ms。优化 D 把 `leaves_to_triangles` 向量化,
把三角形从 13 ms 降到约 2 ms。进程中配对的 benchmark
(合成 640x480, reps=5):

**表 12. A-D 优化后整管线配对 benchmark(合成 640x480, reps=5)。**

| stage                 | old                | new               | speedup                                     |
| --------------------- | ------------------ | ----------------- | ------------------------------------------- |
| partition             | 72.3 ms            | 33.8 ms           | 2.14x                                       |
| triangles             | 8.3 ms             | 2.2 ms            | 3.79x                                       |
| render                | 28.1 ms            | 8.4 ms            | 3.35x                                       |
| palette (amortised)   | 22.0 ms            | 4.9 ms            | 4.47x                                       |
| **whole frame** | **129.0 ms** | **59.5 ms** | **2.17x (~16.8 FPS processing-only)** |

应用级前后对比(同一台机器,同一输入):TOTAL 130.5 -> 62.0 ms,
ΔE2000 11.014 == 11.014, PSNR 15.68 == 15.68, **0 像素不同**。

**Step 4: 帧间抖动(根因)。** 把相机保持不动,镶嵌图仍然每帧闪。
为了弄清为什么,我在 `code/task4_verify.py` 里做了 headless 探针:管线在
四个合成序列(同一帧、噪声 sigma=2、冻结几何、每帧 +1.5 亮度斜坡)上
被驱动,在每个序列上量"普通帧"和"调色板重建帧(每 10 帧一次)"两类
帧的每帧画布跳动。这里的跳动指最大通道变化超过 8 个灰度级的像素比例。
下面这组探针结果就是本步所有数字的来源:

| 序列 | 普通帧的每帧跳动 | 调色板重建帧上 |
| --- | --- | --- |
| 同一帧 | 0.000% | **画布 76.6%** |
| 噪声 sigma=2 | 0.55-0.96% | **画布 76.7%** |
| 噪声,冻结几何 | 0.31-0.59% | **画布 76.7%** |
| 亮度漂移 | 2.85-8.07% | **画布 76.7%** |

也就是说:普通帧每帧最多跳动几个百分点,但一到重建帧,画布在 76.7%
的像素上跳动。三个相互独立的原因从这次探针里冒出来。

主导原因是 K-Means 不稳定。重建会从 OpenCV 的全局 RNG 重新跑一次
`cv2.kmeans`,每次都落进不同的局部最优,而每个三角形的标签都要对着
新调色板重定,所以一个不同的最优会在同一帧里给大部分画布重新上色。
把同样的像素不重新播种地喂给 K-Means,得到最大调色板 delta 为 **180**
(探针里的 `pal_d1` 列);加上固定种子后,同样的输入把 delta 塌到 0,
但是两个不同噪声帧加上同一个种子仍产生 delta **144**。仅重新播种解不了
这个,所以我必须去攻击重建本身,而不是它的随机种子。

第二个原因是管线在任何地方都没有时序一致性。分区、均值和量化每帧
从带噪声的像素重算,所以传感器噪声在 3-5% 的单元上把差点胜出的拆分
决策挪来挪去,在约 3% 的单元上把调色板边界附近的标签翻转。没有东西
锚住输出,即便是一个静止的场景也在漂。

第三个原因是相机自动曝光和白平衡漂移,它把另外两个放大。1.5/255 每帧
的亮度斜坡就足以把每帧画布跳动从约 0.5% 抬到 2.9-8.1%。所以即便我
修了 K-Means 并加了一致性,一个未锁的相机曝光仍会持续让输出跳动。

**Step 5: 修复 (A+B+C)。** 修复 A 是从上一帧调色板热启动,精修上一帧
的局部最优而不是跳到一个新的,加一个死区,在没有哪一项移动超过 2
个灰度级时丢掉重建。修复 B 是在关键帧签名说场景没变时复用分区;
静态帧保留同样的叶子,均值仍从实时像素重新抽取。修复 C 是量化滞后:
每三角形带一份标签记忆,除非另一个调色板项以相对裕度胜出,否则保留
上一帧的标签。测量(跳动 = 最大通道变化超过 8 个灰度级的像素比例):

**表 13. 帧间抖动修复(时序一致性 A+B+C):前后对比。**

| metric                                    | before           | after                         |
| ----------------------------------------- | ---------------- | ----------------------------- |
| palette delta on rebuild, identical input | **153**    | **1**                   |
| steady per-frame churn, noise sigma=2     | **2.400%** | **0.064%** (37.7x less) |
| rebuild-frame churn, identical frames     | 0.013%           | **0.000%**              |
| rebuild-frame churn, noise sigma=2        | 0.029%           | **0.000%**              |
| app static TOTAL ms (temporal OFF -> ON)  | 68.9             | **27.5**                |
| partition stage ms                        | 37.7             | **0.2** (reused)        |

第 4 步量出的重建帧闪(每 10 帧一次、76.7% 像素)不见了——重建现在是
精修而不是重新上色;连续爬动在真实传感器噪声上降约 38 倍;分区阶段在
静止场景上消失。注意两个调色板 delta 数字不同:第 4 步的 **180** 是
只测调色板的微探针(`pal_d1`,不重新播种),而表 13 的 **153** 是时序层
上量到的应用级冷 vs 热重建——它们是两次不同的探针,表 13 拿第二次来
比修复前后。

**Step 6: 渲染复用与行游程均值(opt E)。** 在静态场景上还剩两项每帧
成本:均值(约 14 ms)和渲染(约 10 ms)。E1:精确的 **行游程均值**——
三角形的每一半在每行是一段连续像素游程,所以一个每行前缀和表用两次
查找就能答出一行的游程;逐字节相同是可证明的(精确整数和 < 2^24,
所以 float32 能精确装下,加法顺序不能改变值)。`task4_verify` 断言
max|diff|=0:14.2 -> 7.7 ms (1.85x)。E2: **渲染复用**——画布是
`(tri, labels, palette, shapes)` 的纯函数;当几何被复用而 labels+palette
逐字节相同时,缓存的画布就是该图,所以跳过光栅化(在静态场景上 10 -> 0 ms;
在有噪声时它正确地不发火,因为 labels 变化)。在静态场景上的叠加效应:
基线 68.9 ms →带时序一致性(step 5) **27.5 ms** → 再加 opt E **11.4 ms**,
整体约 6x,全是精确复用,无品质代价。注意下面 step 8 引用的 37.1 FPS
是 *step-5* 的数字(1/27.5 ms),在 opt E 出现之前量到;交付的静态数字是
11.4 ms,约 88 FPS。我把两者都留着,因为每个都是当时那个 build 的真实
测量,但它们不可比,我本不该把 37 FPS 当作终态。

**Step 7: 显示面板。** 两处表现缺陷修了:HUD 之前在实心黑底色块上
画 14 行,覆盖渲染面板约 35-40% x 30-35%(现在是 1 块半透明面板上 3 行,
约 15% x 3-4%);以及调整 `WINDOW_NORMAL` 窗口大小会把砖拉伸(改成把
图像区域做均匀 letterbox 缩放修好,所以 OpenCV 的拉伸变成了恒等)。

**Step 8: 复用冻结颜色 + 相机 AE/WB 锁。** 即便在 A+B+C 之后,静态
场景仍显示残余颜色跳动(0.101% 像素/帧),因为均值和量化仍在每帧重跑。
修复是:在分区被复用时,也冻结上一帧的标签加画布,这样一个不变的场景
在一帧到下一帧是逐字节相同的。我还把相机的自动曝光锁上(`--lock-ae`,
可选在固定的 `--exposure`),并把它的自动白平衡锁上(`--lock-wb`,
一个独立 flag),因为一个稳定的曝光才是让冻结颜色安全而不是陈旧的
前提。两者都是可选 flag,不是预设行为——`quality` 预设只设 `scale`、
`budget` 和 `K`,所以一个跑默认的读者会得到漂移的曝光,除非他们传
这两个 flag,下面的失效情形也一样。测量:跳动 0.101% -> **0.000%**,
静态有效 FPS 22.6 -> **37.1**。我在真相机上确认了抖动明显减小而
保真度没有变差。

### 6.6 真实场景下的鲁棒性,以及测出改动的汇总

真实场景下的鲁棒性归结为四种不同的失效模式,每一种我都用测量
而不是用意图来回答。证据在指名的章节里。

* **它在未见内容上保持在固定限制之内吗?** 分区器构造上不可能超过
  预算——四叉树 guard 是 `while heap and n_tri + 6 <= max_triangles`,
  而 `region_merge_partition` 在超出预算时直接 raise 而不是返回一个
  超预算的分区。PDF 的另一条硬约束,无间隙无重叠,是被验证的而不是
  被论证的:`code/verify_coverage.py` 检查三个交付的铺覆,发现单元
  互不相同且网格对齐,每个单元的两块三角形满足精确面积恒等式
  `area(a) + area(b) = s²`,且光栅化裁剪中 **0 个未覆盖像素** (§1)。
* **它在 deadline 下能活下来吗?** §6.4 整节按阶段、按前后配对测量,
  从 2,140 ms 到 59.5 ms 每移动帧,空间优化在 0 像素不同下精确。
* **它在帧与帧之间视觉稳定吗?** 时序层和它测出的跳动数字在 §6.4
  step 8;静态场景上的跳动 0.101% → 0.000% 像素。让这件事安全的
  条件——锁住的曝光——在那里被说出来了而不是被假定,我点明了 flag
  是 opt-in 的。
* **它在不是为它设计的内容上表现如何?** §6.5 在 7 个场景上跑,
  跨度人像、强纹理、饱和颜色、低光、逆光织物和一面近乎过曝的墙,
  并报告失败的那一个配置而不是只报告成功的六个。

哪里鲁棒性 *没有* 确立,我宁愿这样说:这是一台机器上的单个相机
(§9),Task 2-3 的测试内容是一张图,时序层特意用一点点保真度换了
稳定性。

我在 §6.4 做的每一个优化都是一对前后对照,带阶段 ms、整帧 FPS、
ΔE/PSNR 和一项像素 diff 检查,所以每一处改动都用促成它的那个测量
来记录。把头一句话读顺只有在每个数字的测量条件都被附上时才行。
带着这个想法,把三种容易混淆的事分开:

* **全质量配置下每帧成本,移动输入。** 优化前 2,140 ms → **59.5 ms**,
  即在合成帧上约 16.8 FPS 仅处理(表 12)。一处中间构建,在两项
  O(T·H·W)/按候选修复之后、渲染和均值工作之前,测到约 215 ms (约 4.6 FPS);
  那是一个路标,不是交付数字。
* **静态场景上的同一管线。** 68.9 → **11.4 ms** (约 88 FPS),用
  精确空间复用。step 8 里的 37.1 FPS 是这一步(27.5 ms)的 step-5
  测量,被超越。
* **相机自身的天花板。** 它 31-33 FPS 的读回是一个独立的极限,
  这些优化不能改变它。

空间优化是精确的,在相同输入上 0 像素不同。时序层(调色板节奏、
热启动、死区、滞后、复用即冻结)是一个为了稳定性做出的、刻意的
逐帧近似,它的确用一点点保真度换了稳定性,这就是为什么配对比、
而不是绝对 FPS,才是这里可信的数字(见 §6.2)。

### 6.7 Task 4 中发现的问题与解决

0.45 FPS 的基线来自两个主要肇事者:那个 O(T·H·W) 的均值阶段和
分区里按候选的 numpy 均值(§6.2)。我用单元内均值、SAT 表、批渲染、
预算好的优先级、调色板节奏和向量化三角形把它们修了,细节在 §6.4。

第二个问题是边带污染的均值,这是交付参考实现里的一个潜在 bug,
也影响了我的 Task 2/3 运行。修复在 §6.4 step 1,测量在 §6.4,我也在
那里声明了它对记下的 Task 2/3 数字的残余影响。

K-Means 调色板的不稳定是第三个问题。全局 RNG 加上在近乎退化数据上
10 次重启的组合在帧与帧之间翻转局部最优(§6.4 step 4)。我用热启动
加死区加复用加 AE/WB 锁修了它(§6.4 step 5 和 8)。

两处表现缺陷也需要注意,即 HUD FPS 错报和调整大小时的窗口拉伸。
它们的修复在 §6.3 和 §6.4 step 7。

最后,`build_palette` 的 "异常" 其实是一个 2 样本的测量假象,不是
真实的性能问题,我在 §6.2 里搞清楚了。

### 7.1 GenAI 如何理解任务

这段工作里,最让我看清模型实际推理方式的有三个片段。

第一个是"能跑但心智模型错了"的代码(Task 3 的四叉树循环)。我的
guard 写成"一直分裂到预算内",恰好与它该做的相反。代码无报错地跑完了,
只有仔细对照意图(分裂会让数量增加)才暴露出来。我得到的教训是:
AI 生成的代码即使能执行,也需要对照它"应该做什么"来做个 sanity check。

第二个是 Task 4 的成本诊断。AI 正确指出瓶颈是 Python 到 numpy 的调用
次数,而不是算法复杂度,而它追问"精确还是近似?先说明不变量"为后面
每一个优化定了调,让每一项优化在构造上就是精确的。

第三个是 AI 与多数助手共有的偏差,在 Task 3 的 S_max=64 片段里看得
最清楚。我请它挑 S_max,它用 64 赢了的四项指标打头、把唯一的回归
(ΔE2000)压成一个括注,报出"64 是明确赢家"。只有我推回去之后,它
才按区域拆解 ΔE,发现阴影区域在 64 下确实明显更糟。我学到的是:模型
会把自己的回答框成我早先暗示过的那个假设,并且不会主动指出客观指标
与人类感知会反转。

### 7.2 来自 GenAI 的决策

几个具体建议塑造了设计,所以我记录那些经得起测量和经不起测量的。
铺覆方案(正方形格子被一条对角线切开、按棋盘奇偶交替)和三种颜色
量化器的对比(multi-Otsu、K-Means K=3、固定百分位)来自第一次设计对话。
一个被提议的边缘密度分裂优先级经过测量后被否:它给出网格里最差的
Edge F1 和唯一的负 EPI。两个建议在消融后被回滚——一个几何冻结变体
让质量明显下降,和一个边框处理,人眼更喜欢原来的。其余建议——RDO
四叉树、K-Means-Lab 调色板、热启动重建、调色板节奏、批渲染、预计算
优先级、渲染复用——都被采纳,每个都在对应章节配了前后测量。

## 8. GenAI 的局限与改进空间

这一节是我自己的评估,因为这个工具的局限不在它产出的代码里可见,
而在我不得不停止信任它的地方。四个 task 上反复出现四种模式,我按
它们让我付出的代价排序:塑造我结论的那个偏差、代码本身不可靠、
模型不愿去查东西、以及一个随项目变大而变严重的记忆问题。

第一、最有后果的模式是,一个 agent 在一次会话里会朝用户已经说出的
那个东西收敛。我注意到它是我提出把 S_max 抬高会给四叉树更多细拆分
的空间时,模型立刻同意,然后设计了一个只能证明我的假设的实验。它
从未问过这个前提值不值得质疑。同样的偏差在结果出来时又出现:
模型报 "S_max=64 是明显的胜者",做法是把 64 胜的四个指标摆在前面,
把唯一矛盾的那个指标 ΔE2000 降级成括号。那段矛盾的分析——阴影区
在 64 下明显更差——只是在我反推之后才出来(§5.4)。最让我担心的是
第三种变体,模型把指标结论当作感知结论。四个客观指标偏好 64;我
自己的眼睛偏好 32;模型没有预料到这两者可能不一致,所以它没有
注意到时差的框架。

我得到的不是错的答案;我得到的是一个流利的、来自一个已经把我框定
当成自己的模型的答案,而在一次连续会话里没人去注意到。真正帮到
我的做法是结构上的而非巧妙 prompt:项目后期我开始把同一份草稿跑过
几次独立的 review pass,每个被指示从一个不同的角度攻击它,让它们
相互不同意。一个没有对话上下文的第二读者比继续同一次会话的同一个
读者难骗得多。

第二种模式是生成的代码跑得通但不对。§5.5 里的四叉树是最清楚的
例子:拆分的 guard 被写成 "如果三角形数低于预算就返回",循环被写成
"超出预算时继续拆",这是一个看起来连贯的、把 "拆分会减少三角形数"
这个信念编码进去的写法。它做的事情正好相反。代码编译、跑、产出一份
看起来合理的镶嵌图,安静地用掉了 9,990 中的 4,320 块砖。什么都没
报错;唯一的症状是我量到的边缘对齐分略为负。我是从重读代码本想做
什么、而不是代码说了什么这件事上发现它的,同类的错误又出现了两次,
在合并候选对齐和在网格步长扫描上。我采用的缓解是本报告从头到尾在
演示的那一个:把每一处优化当作一个关于不变量的主张,并写一条断言,
如果那个主张错了它会大声失败,而不是去信任看起来对的代码就是对的。

第三种模式是模型不会去查东西,除非被告诉去查,而当它真去查时它
可能查得不够彻底。它建议在 Lab 空间上用 K-Means 做调色板,却没有
提到 `cv2.kmeans` 依赖一个全局 RNG,所以调色板在跑与跑之间不可复现。
它推荐边缘密度拆分优先级,却没有指出 per-region 算的 Sobel 方差和
全局算的在区域边界附近不同。在两个 case 里,缺的那个信息会改变我
怎么跑那个实验,而两者都没主动给出来。我自己版本的这个问题更微妙:
不是一个捏造的事实,而是一个被自信推荐的算法,它主要的缺点我自己
必须在测量中发现。

第四种模式是一个上下文记忆问题,它正是因为这个项目变长才冒出来。
随着报告积累了数字、图片和决策,助手开始跟不上"哪些已经确立",
几次产出了与它自己更早记录的数据相矛盾的数值,或者与磁盘上证据
对不上的数字。我在审计最终稿时找到的错正是这一类的:与同一份报告
里别的数字不一致的值、描述的内容文件里并没有的图注、以及个别
干脆是编出来而不是量出来的量。这些没有一个是出于恶意,大多数孤立
看都很合理;它们来自模型在一个对它来说太长的上下文里推理,无法
把每一个早先的主张都记住、再拿它去核对每一个新主张。由此我得出一
条没有例外的规矩:对这么大的一份报告,每一处数字、图片和代码引用
都必须通过独立的交叉审核或人工对着源文件复检,因为模型自己的自信
并不是一个数字是否真实可靠的信号。

如果我能换一个未来项目,我主要会改过程而不是改模型。我会把对抗性
review pass 从一开始就放进去而不是放到后期,因为它是我找到的唯一
一个能稳定打破一致性的机制。我会要求任何关于库行为、指标定义或
已发表方法的主张,都必须有参考或我自己跑过的一份验证来支撑,而不
是因为它听起来对就被接受。我会把助手当作一个快同事,它的提议是
要被检验的假设,而不是一个权威,它产出的只是要被格式化。本项目中
管用的部分是那些我在检查的部分:量前后、写不变量、并愿意在数字
不同意时拒绝一条建议。失败的部分是那些我停止检查的部分。

## 9. 结论

我搭了一个三角砖图像生成系统,把一张图转换成 10,000-砖预算下的
直角等腰三角形镶嵌图,并走完了作业的四个 task。

在 Task 2 中我用 10 项指标套件建立并展示了
颜色量化方法比几何次要。在这张亮度主导的场景上 Otsu 和 K-Means
彼此接近,朴素的固定阈值在边缘指标上胜出而在颜色指标上落败。
均匀网格的负 EPI 量化了几何与内容错配的程度。

Task 3 让几何变成自适应(RDO 四叉树),让调色板变成多色
(K-Means-Lab)。在 `sky.jpg` 上一次 15 次扫描加一份率失真研究显示
预算最好花在哪:K=16, S_max=32 作为折中,ΔMSE 优先级,四叉树。
S_max=32-vs-64 的结果我把它呈现为一个双侧取舍,而不是单一胜者,
出于两个原因:这次扫描是单图证据,而一个强色相的场景可能搬动
调色板方法和 K 的排名;且扫描驱动从不播种 OpenCV 的 RNG,所以我量到
它逐次 ΔE2000 散布约 0.4,并在确定性调色板(§5.4)或播种运行(§5.6)
上重新锚定了颜色侧 ΔE2000 差距小于那个值的比较。把那个下限的作
用和不覆盖的范围说精确:每个指标各有自己的下限,§5.2 把每一次对比
列在它匹配的那条下限下。K 的结论依据一个 ΔE2000 差距 2.34 对 0.441
的下限 (5.3x);S_max 和优先级的结论依据 2.9x 到 34x 自己下限的结构
差距。三次对比 *没有* 跨过各自的下限,我已点明这一点而不是依赖
它们:S_max 取舍的颜色侧、S_max 64-vs-128 这一步、以及优先级对比
的颜色侧。调色板选择是个诚实的边界——ΔE2000 上 1.5x,而 Median-Cut
在四个结构指标上更优——§5.6 把它的两面都写出来而不是宣称胜利。

在 Task 4 中我把管线变成实时相机循环,并处理了离线 task 从未
练过的真实世界问题:一个占了 75% 帧时的 O(T·H·W) 均值阶段、
AI 引入的四叉树 bug、一个潜在的边带缺陷、来自不稳定 K-Means
和相机曝光漂移的帧间抖动、以及一个误导人的 HUD。我把每一处都
量了前后;在静态场景上循环跑到每帧 11.4 ms,约 88 FPS (headless,

## 附录 A. 评估指标的定义

图像质量的数字来自 `code/brick_metrics.py`;时间数字来自
`code/brick_io.py` 里的 `StageTimer`,边际收益数字来自
`code/task3_marginal.py`。本附录覆盖质量指标,它们是那些含义容易被
误读的那一组。每一条对同一份渲染回答一个不同的问题,所以结果可以
不带猜测地读。

**PSNR** (越高越好) 是源图和渲染之间的峰值信噪比,逐通道在全图上算,
以 dB 为单位报告:

    PSNR = 10 * log10( MAX^2 / MSE ),  MAX = 255

它是这里最熟悉的数字也是最没区分力的,因为一个大的均匀颜色偏移
花的代价和小结构误差一样多。

**SSIM** (越高越好) 是 Wang 等人(2004)的结构相似性指数,在最多 7x7
像素(只在图像维度强制时更小)的滑动奇窗口上逐通道算并取平均。SSIM
打分局部对比和亮度结构,而不是原始像素一致,所以它对模糊或结构性
位移的渲染的惩罚比对均匀亮度偏移的更重。

**MS-SSIM** (越高更好) 是在四个逐级降采样分辨率上算出的 SSIM 得分的
均值,层级之间用高斯金字塔降采样(`cv2.pyrDown`)。跨尺度取均值
奖励跨降采样存活下来的结构,所以它难以用一个好的低分辨率匹配
加最细尺度的噪声来满足。这是一个逐层 SSIM 的四层算术平均,
是 Wang 等人(2003)加权公式的简化,不是标准的 MS-SSIM 加权,
本报告里的数字应被读作一种多尺度一致性检查,而不是一个能与
文献对比的分数。

**ΔE2000** (越低越好) 是源和渲染之间逐像素的 CIEDE2000 颜色差异的
均值,在把两者从 sRGB 经 CIE Lab 转换后算(Sharma 等人,2005)。
它是这套里的感知颜色指标;粗略地,2 以上是肉眼可见的颜色差,
本报告里的数字(约 6 到 12)对应于并排查看时显然的差异。

**Edge F1、precision 和 recall** (越高越好) 比较源和渲染的 Canny 边缘
图,两者都用 `sigma = 2.0` 抽取。因为一条三角砖边界可以落在离真实
边缘一个像素的位置而仍然看起来对齐,每张边缘图被 3-像素容差膨胀,
当一个边缘像素落在另一张图的膨胀版里就算匹配:

    precision = |render edges near a source edge| / |all render edges|
    recall    = |source edges near a render edge| / |all source edges|
    F1        = 2 * precision * recall / (precision + recall)

注意这两个比值用了不同的参考集:precision 问的是镶嵌图画出来的东西
有多大比例是真实结构,recall 问的是真实结构有多大比例被镶嵌图复制了。
膨胀是单侧的,所以一个刚好落在容差带外的匹配会被两边都漏掉。

**EPI,边缘对齐相关** (有符号,越高越好) 是源和渲染的均值化 Sobel
梯度幅度场的 Pearson 相关:

    EPI = corr( |∇ source| , |∇ render| )

它度量镶嵌图里的边缘能量是否与源里的边缘能量共定位,与总强度无关。
正值意味着两者在边缘的位置上达成一致;负值意味着它们不一致,
在这个项目中是不跟随图像内容的三角砖边界的签名。因为幅度是稀疏
且重尾的,一份正确的镶嵌图仍然接近零打分,所以符号是这个指标
可靠的那一部分。

那带来一个我应该明确说出来的影响,因为报告其余部分倚靠 EPI 差:
因为一份好的镶嵌图落在零附近,*两份好镶嵌图之间的绝对量比较没
有意义*——+0.045 和 +0.015 都是 "接近零且为正",而它们之间的比值
不是这个指标定义出来的量。在我对配置之间比较 EPI 时(§5.2、§5.6),
我把它用作一个 Edge F1 也向同一方向移动的配置上的符号和排序信号,
从不当作独立效应量,并把每一条这样的主张对照我量到的 0.0021 逐次
散布来检查。唯一一条依据 EPI 的 *符号* 而非其大小的对比是
Sobel-priority 那一行,它是这次扫描里唯一一份真的会变负的配置。
这个名字是本报告的局部命名:它就是一份 Sobel 幅度的 Pearson 相关,
不是图像融合文献里的 Edge-Preservation Index。

**Quantisation error** (越低越好) 是每个三角形自身的均值颜色与
分配给它的调色板项之间的平均 CIEDE2000 距离。它把管线的颜色量化
那一半和几何那一半隔开,因为它从不看渲染图像。一份高 quantisation
error 配上合理的 PSNR 意味着几何没问题但调色板表示不了这张图,
这就是在 §4 中把 K 扫描和 S_max 扫描分开的那个诊断。

**Budget utilisation** 不是质量指标,而是 10,000 砖这次运行吃掉的比例,
`N / 10000`。所有 Task 3 运行落在 0.998 到 0.999。

**套件的框架。** 这些指标被有意做成不冗余的。PSNR 和 quantisation
error 看颜色;SSIM 和 MS-SSIM 在一个和多个尺度上看结构;ΔE2000 看
感知颜色距离;edge F1 看检测到的边缘是否重合;EPI 看边缘能量是否
共定位;而图 3 的残差图展示两图在哪里不一致,而不是不一致有多少。
它们之间的分歧,而不是任一单独的分数,是 §4.2 和 §5.2 中结论的来源。
